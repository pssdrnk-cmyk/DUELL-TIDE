# jam/: the checks and the test tools

## Fast tests (`check.sh -j`, `--changed`; `repin.sh`; `merge_branches.sh`)

`sh jam/check.sh` alone is the serial run it always was. These options switch to `jam/fastcheck.py`:

- `-j N` (or `--all`): the host groups N at a time. Each group runs `sh host_tests.sh GROUP` in its own sandbox (links to the checkout, a private `felucca-base/build`), so no two share `build/host`, `build/*_mut`, ... Without a number N = free GB / 0.8 (one -O2 compile of a test program peaks at about 340 MB), at most cores - 1 and **at most 4**; it is printed. Higher with `-j N` only when nothing else is building: a `-j 8` run on the owner's PC used up Windows' process table ("fork: Resource temporarily unavailable", Git Bash sessions of other lanes included), so the limit there is processes, not memory; at most 4 jobs at once across all lanes. The verdict per group is decided as in the serial loop; `-j 1` is the serial run with the cache.
- Compile cache `felucca-base/build/host-cache/` (`jam/ccwrap/cc`): a one-file `cc ... -o OUT x.c` is keyed by the preprocessed text + flags + compiler version, so an unchanged program is never built twice (re-runs, groups with the same build). `--no-cache` turns it off; `rm -r` the folder to clear it; `stats.log` counts hits / misses.
- `--changed [BASE]` (default `fork/b9`): only the groups whose sources changed since BASE (committed, working tree, untracked). The map `felucca-base/build/host/groupmap.json` (group -> the files its programs compile, from `cc -MD`, and the files its `host_tests.sh` case, scripts and test sources name) is rebuilt by itself when `host_tests.sh`, `jam/fastcheck.py`, a file list or an `#include` / import / path line in firmware / tests / tools / web changed (about 15 s); every run also records what its compiles really read (`build/host/groupdeps/`), which `--changed` adds to the map, and a group never run here counts as reading the whole firmware. A change to `host_tests.sh` selects the groups whose own case changed (all of them if the shared part did), docs only runs `check_docs`, the device build runs when firmware or tools changed. Most firmware files are compiled into every program, so a change there selects nearly every group: `--changed` helps with tests, tools, one group's data and docs. `python3 jam/fastcheck.py --changed BASE --list-changed` only prints the groups.
- Measured (WSL, b10 tree, 192 groups): serial 51 min; `-j 2` 26 min; `-j 2` with a warm cache 8 min (the slowest groups, `tcmeas` 273 s and `twocore` 197 s, set the floor); on the Windows PC with `-j 8` 13 min cold, 6 min warm. PASS / FAIL / SKIP per group equals the serial run's in every run. 298 compiles, 293 distinct: the cache pays on re-runs, not within one run. A firmware edit selects nearly every group (about 17 min at `-j 3`); test, data and docs edits select a handful.
- Timings under WSL on the b10 tree (193 groups): full run cold at `-j 8` 702 s (11.7 min, 186 PASS / 0 FAIL / 6 SKIP; before the process-table incident); a one-file firmware edit with the cache warm, `-j 4`: `fx.c` 178 groups in 564 s, `tide_ui.c` 176 groups in 1002 s, `editor.c` 175 groups in 455 s. Any firmware edit changes every program that includes it (the firmware is one translation unit), so the compile cache cannot help after one; the rest is the test programs' own run time (compiling is about 70% of a cold run). A group `emu` without a usable emsdk is a SKIP, also when `--changed` names it.
- `--host-only` (no device build, no jam tests; the serial loop honours it too and generates the headers first), `--shard I/N` (the CI split), `--out FILE`, `--summary FILE` (markdown: every failed group and its first failing line). CI (`host-tests.yml`) runs its shards this way, cores - 1 groups at a time; a failure never stops the others.
- `python3 jam/fastcheck.py --verify-map ...` lists the files the recorded compiles read that the static map did not find (the recorded ones cover them).

`sh jam/repin.sh CAUSE_COMMIT [group ...]` after a change moved test hashes: it runs the groups on HEAD (scratch worktree), finds the new value of each `#define NAME 0x..ull` / `static const uint64_t NAME[] = {...}` pin by running the test with its comparisons printing what they saw, reverts CAUSE_COMMIT in a second scratch worktree and runs the groups there with the old pins. Only the groups that pass without the cause are written (comment `(b9: <cause subject>, proven by revert; was OLD)`), `golden.txt` / `multi_render_golden.txt` / `union_golden.txt` regenerated, then the groups run on the checkout. The table lists group, pin, old -> new, proven. The group `emu_smoke` is covered too: its pins are the screens' CRCs in `tests/emu_smoke_ref.txt`; after the same proof by revert, a screen whose stored CRCs do not include the one the tree draws gets the new CRC (other machines' CRCs of that screen are dropped: the CI prints the Linux ones), the other lines stay, and the checkout is re-run (its generated headers are rebuilt first). Not covered: a changed reference model or a changed test, not a hash (the table says "no hash pin moved").

`sh jam/merge_branches.sh BASE branch [branch ...]` merges in order on the current branch. A conflict in a generated file (`jrny_ctx.h`, `tools/factory_multis/M*.bin`, `tools/drone_multis/M*.bin`, the three golden files) takes our side as a placeholder and is regenerated afterwards (`jrny_ctx gen`, `factory_multis.py build`, `drone_pack.py`, `GOLDEN_UPDATE` / `MULTI_RENDER_UPDATE`); a conflict in anything else stops with the list and the merge in progress (fix, `git add`, `merge_branches.sh --continue BASE`). At the end `check.sh --changed BASE` (`--no-check` skips it). `--hand-from REF` takes REF's files for the hand-written conflicts (to replay a finished integration).

## Cleanup (`jam/cleanup.sh`)

`sh jam/cleanup.sh` (a dry run) lists every worktree (clean / dirty, branch or detached, merged into `fork/jam11` or `fork/b9`, directly or as patch-equivalent commits by `git cherry`) and every branch of the fork remote (merged, open PR head from the GitHub API, protected `b8 b9 b9-release jam11 main stable`), with the verdict. An unmerged branch is never a delete candidate: its unique commit subjects are shown for you to judge. `--apply` makes `refs/backup/<date>/` refs (`wt-<folder>` for a worktree, the branch name for a branch) and removes only clean, merged worktrees that are not the main or the current one nor on a protected branch, with `git worktree remove` and never `--force`. The `git push fork --delete ...` line is printed, never run, and withheld when the open PRs could not be read. `--from-refs refs/backup/<date>` judges those saved tips instead of the live remote (replays a cleanup afterwards); `--no-fetch`, `--no-pr`, `--into "A B"` as `--help` says.

The keep list `jam/cleanup.keep` (one worktree folder or branch name a line, `#` comments; seeded with b7-pkg, duell-jam11, b9-release and the protected branches) is never removed or deleted by `--apply` and shows as "kept (keep list)".

## Running things in WSL safely

**Never hand shell syntax to `wsl.exe` in a quoted string.** `wsl.exe` without `-e` pastes its arguments together and runs them through WSL's own shell, so the single quotes you typed in Git Bash are gone: in `wsl.exe bash -c 'D=/x; rm -rf "$D"/*'` the assignment `D=/x` is only an argument of `bash -c`, `$D` is empty in the outer shell, and the command that runs is `rm -rf /*`. On 2026-11-12 exactly that emptied a home directory (dotfiles, `~/venv`, `~/emsdk`, every mirror; it could not remove `/home/<user>` itself, so the folder kept its birth time). Check it harmlessly: `wsl.exe bash -c 'D=hello; echo "[$D]"'` prints `[]` (`wsl.exe -e bash -c ...` prints `[hello]`; `--` does not help).

- Put the commands in a script file and run `wsl.exe -d Ubuntu -- sh /mnt/c/.../script.sh args` (what `jam/wslmirror.sh` does), or use `wsl.exe -d Ubuntu -e bash -c '...'`.
- In any script, before an `rm -rf "$X"...` or an `rsync --delete` into `$X`: `. jam/safe.sh` and use `safe_rm ROOT "$X"` / `safe_under ROOT "$X"`; they refuse an empty path, `/`, `$HOME`, a `..` and anything not strictly inside ROOT. `wslmirror.sh`, `prune.sh` and `check.sh` do; `jam/test_safe.py` tests the guard and fails on a repository script that passes a quoted shell string to `wsl.exe` without `-e`.
- Rebuilding a wiped WSL home: the default dotfiles (`cp -an /etc/skel/. ~`), `~/venv` (`python3 -m venv ~/venv && ~/venv/bin/pip install -r requirements-dev.txt`), emsdk 6.0.13 as the CI's emu job does (`git clone --depth 1 https://github.com/emscripten-core/emsdk ~/emsdk`, then `~/emsdk/emsdk install 6.0.13` and `activate 6.0.13`).

## WSL on its own disk (`jam/wslmirror.sh`)

`sh jam/wslmirror.sh [check.sh arguments]` (from Git Bash, PowerShell or WSL; no arguments = `-j 4 --host-only`) mirrors the worktree with rsync to `~/duell-build/<folder>` on WSL's own disk, builds and tests there and copies only the logs back (`felucca-base/build/check/<sha>/` in the worktree). A build over `/mnt/c` costs 15 to 50% more on a single group (`multi` 14 s against 12 s, `sounds` 21 s against 14 s, same tree, no cache). The mirror keeps its own `felucca-base/build` (generated headers, compile cache), which rsync never touches, so the next run starts warm; `.git` is not copied: the mirror has a repository of its own (`git clone --shared` of the shared one, refs fetched each run, HEAD and index set to the worktree's HEAD), so `--changed` and the git-reading groups work, commits happen only in the Windows worktree and the shared repository is never written. It needs `rsync` and `~/venv` (Pillow, fontTools: `requirements-dev.txt`) in WSL, as `jam/wsl.sh`. Same limit: at most 4 jobs across all lanes. The script never sets `GIT_DIR` / `GIT_WORK_TREE` (a test that makes its own scratch repository would then write into the real one: an earlier version did, and left a `core.worktree` in the shared config that broke every git command on Windows), and it refuses to run, and complains after a run, if the shared config has a `core.worktree`.
- Timings on the mirror, 193 groups, `-j 4`: full run cold 1037 s; a one-file edit with the cache warm (a code line appended): `fx.c` 172 groups in 375 s (6.2 min), `tide_ui.c` 171 groups in 358 s (6.0 min), all PASS. (The earlier 564 s / 1002 s on a plain clone were noisier: other lanes were building.)

## Changelog and roadmap fragments (`changes/`, `jam/assemble_changes.py`)

A branch no longer edits the shared lines of `CHANGELOG-TIDE.md` / `docs/ROADMAP.md` (every integration conflicted there). It adds a file `changes/<branch>.md` instead:
- `## changelog` and `## roadmap` parts, each with `### <target>` headings and bullet lines under them (format and an example: `changes/README.md`);
- the target is a `## <name>` section of the file, or in the roadmap a bold label `**<name>**` (`### 1.0.0-b10`, `### Repository and CI`, `### Later, in order`);
- at RC time `python3 jam/assemble_changes.py` (`--dry-run` to look first) adds all fragments to the end of their targets, in file-name order, deletes them, and runs `jam/check_docs.py` on the result (a failure puts the two files back);
- an unknown target stops the run before anything is written. Striking or rewording an existing row is still an edit of the roadmap itself. Test: `jam/test_assemble_changes.py` (two fragments for one heading both land).

## Every group runs by default or says why not (`jam/check_groups.py`)

`host_tests.sh` names its groups twice: the default list (`want="${*:-...}"`, what CI's shards and `--changed` run) and the case labels. A group that is only a case is never run by anyone (`take`, `answer` and `guards` were, until PR 62). `python3 jam/check_groups.py [host_tests.sh]` (the `jam-tools` CI job) fails, naming the group, when a case label is neither in the list nor marked out by a line `# not default: LABEL - reason` (just above its case; the reason is not empty), when a marked group is in the list, when the list names something that is no case, or when a marker names no case. `$EMU` in the list stands for `emu`. Test: `jam/test_check_groups.py` (drops `take` from a copy of the list and expects the failure).
