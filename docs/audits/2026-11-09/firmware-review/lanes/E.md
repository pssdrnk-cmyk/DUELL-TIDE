## What is solid
- `storage.c` commit order is right on every object: other copy erased, payload, 32-byte commit record last, read back before "saved"; newest valid seq wins with wrap; `st_wipe` erases the non-current copy first. A power cut at any step leaves the old record or the new one, never half. Patch chunks, multis, patterns, settings (TIDE tail inside), wavetables, velocity record and autosave all go through it; the FM6 voice bank's own staging (autosave's older copy, then 0xE7000, finished at boot) is power-cut safe too, and an autosave that takes the staging sector ends the transfer (rc 5).
- Every editor transfer (backup PUT, PATCH_RAW, WT_PUT, FM6B): arguments checked before the transport is stopped; a piece must start at the current position and stay inside the declared length; a missing, repeated, out-of-order or abandoned piece writes nothing; commit checks CRC and the format (`pt_rec_ok` + name, `ed_bk_mul_ok`, `ps_obj_ok`, `wt_obj_ok`, `proj_import`, settings magic / panel / palette). Staging is guarded by `proj_wire_gen`, USB reset and a 15 s timeout. A malformed message can only reach the staging RAM inside its bounds. Backups from a newer build with an unknown format are refused (rc 2), not half-loaded.
- 126-record limit: a new 127th record gets STORE FULL with nothing written (`pt_takes`), and rewriting a saved slot always fits its own chunk (6 x `PT_WORST` + 4 <= `PT_CAP`). Flash is never written while the transport runs, except the pattern-slot write of `ps_take` (an owner decision). Device-side writes are debounced (menu 2 s, TIDE settings 2 s, autosave at most once a minute and only when quiet).
- Updates: the loader checks the package CRC and the chip key before any erase, writes only `0x4000..0x93000`, verifies every sector, skips Felucca's store when clearing records, and resumes after a power cut from the record at 0xE4F00. The app stages only at 0xE0000..0xE4FFF and erases a leftover staging at boot. `BG_START` sends the unit to UBOOT after two dead starts in a row.
- `console.c` is not in a default release build: `FELUCCA_CDC` is 0 unless `DUELL_BENCH` or `DUELL_TEST_MODE` is set (`felucca.c:18-24`), and it is included only under `#if FELUCCA_CDC` (`felucca.c:140`). (One build-script gap: E5.)
- USB SysEx: 640-byte frame, an oversized frame is dropped, any status byte ends a frame (`usb.c:762-812`).

## Findings (most important first, at most 15)
### E1. A sound saved to a slot from the web editor loses its MORPH End B; every later load rolls a new random B  (P2, CONFIRMED, functional)
- **What the player meets:** Shape a sound and its B side (ROLL, or B values set by hand). In the web editor, save the current sound to a slot (Patches, "save current sound": `UP_STORE`). Load that slot later, or after a power cycle: the A side is right, but End B is a fresh random roll, a different one on each load. The hand-set B values are gone. A hold-SAVE on the unit keeps End B. A PATCH_RAW export of that slot has no End B either.
- **Why (code):** `editor.c:826` calls `up_store()` → `up_store_cat` → `up_store_trk` (`upreset.c:1151-1181`), which relies on its caller to set `up_bv_in` (comment at `upreset.c:1167`). Only the device's `up_patch_save_part` does that (`upreset.c:1633-1642`: `morph_ready`, `morph_bv_make`), and every setter clears `up_bv_in` afterwards (`upreset.c:1207,1642`, `up_fm6.c:43`), so on the UP_STORE path it is 0. `pt_encode` then leaves out `PTF_MB` (`upreset.c:811-813`). At load, `up_load` finds no `PTF_MB` (`upreset.c:1310`) and `morph.c:1890-1891` rolls `morph_new_seed()` at the current AMOUNT. The protocol promises the opposite: `web/EDITOR_PROTOCOL.md:277` ("engine, parameters, End B, the arp block") and `web/editor/unit.js:321` ("so End B and the arp block are kept").
- **Test that hides it:** `tests/editor_test.c:1496-1503` ("an editor save = the unit's own save, byte for byte") compares `up_store()` with `UP_STORE`, which is the same function, through `up_rec()`, which does not decode End B (`upreset.c:773`). It cannot see the difference.
- **Fix sketch:** put the four End B lines of `up_patch_save_part` (`morph_ready`, the `ref` build, `morph_bv_make`, set / clear `up_bv_in`) into a small helper, and call it from `ED_UP_STORE` for `song.sel` around `up_store`. About 30-40 B flash, no RAM, main loop only, audio interrupt not touched.
- **Test:** in `editor_test` item159, compare the raw stored bytes (`up_raw_get`) of a hold-SAVE (`up_patch_save_part`) and an `UP_STORE` of the same part with the fader in the middle, and check that `PTF_MB` is set; also check that a load of the slot gives back the same End B (`morph_sig`).
- **Known?** not recorded.

### E2. ERASE DATA also erases the FM6 voice bank and the three WAVE user tables, but the screen does not say so and two guides say the bank is kept  (P2, CONFIRMED, functional)
- **What the player meets:** MENU > SYSTEM > ERASE DATA asks "ERASE ALL MY DATA?" and lists "SETTINGS, FAVOURITES, AUTOSAVE, SAVED PATCHES, MULTIS, PATTERNS." INSTALL.md says "Not erased: the FM6 voice bank" and QUICKSTART says "keeps the FM6 voice bank". A player who trusts this loses the 32-voice bank they loaded (SLOT B1..B32 become empty) and their USR1..USR3 tables (they play a sine). The installer's "Erase my saved data" runs the same erase.
- **Why (code):** `erase_data.c:48` wipes `OBJ_WTAB0..2`; `erase_data.c:64` erases `FVB_HOME` (0xE7000) just before the settings (DUELL 1.1 item 91). The dialog text is `ui_draw.c:3322-3323`; its own comment says the voice-bank line was removed, and the wavetables were never on it. The docs are `docs/INSTALL.md:60` and `docs/QUICKSTART.md:41`. The comment in `editor_erase.c:88` ("the settings are not [gone]") is stale too: since 1.1 every object is tried and rc 4 can come with the settings gone (`erase_data.c:63-76`).
- **Fix sketch:** dialog lines, e.g. "AUTOSAVE, PATCHES, MULTIS," / "PATTERNS, TABLES, FM6 BANK." (check the width against the 200 px rule of item 119); fix INSTALL.md:60, QUICKSTART.md:41 and the `editor_erase.c` comment. About 10-20 B flash, UI only.
- **Test:** the erase group already proves the wipe; add the two doc sentences to `check_docs.py`, or read the dialog strings in the UI test that draws `draw_confirm_erase`.
- **Known?** not recorded (corrects INSTALL.md / QUICKSTART, not a ROADMAP row).

### E3. After a save cut short by power loss, RESTORE of that patch can bring the old sound back at the next power-on, or a new save can lose to it  (P3, CONFIRMED, functional / data)
- **What the player meets:** It is rare and needs a power cut (or a flash fault) in the ~50 ms of the second write of a save that moves a record to another chunk. This happens when a saved sound grew and its chunk is full, so it shows up with a full store. Afterwards the slot looks right. But if the player then RESTOREs that slot (or does RESTORE ALL), the old saved sound is back after the next power-on. If they save a new sound into that slot instead, the old one can come back over it at power-on.
- **Why (code):** a move writes the new record (revision +1) first, then cuts the old one (`upreset.c:927-945`); a cut-short move leaves both in flash, and the scan picks the newer (`upreset.c:486`). The old one is not in the directory, so its chunk's `pt_n` doesn't count it (`pt_tally`, `upreset.c:455-471`). RESTORE rewrites only the chunk the directory points to (`upreset.c:948-952`, `909-923`), and RESTORE ALL's `pt_wipe` skips a chunk with `pt_n == 0` (`upreset.c:1011-1012`), so the stale record stays in flash. At the next boot `pt_scan_all` adopts it again. A new save after the restore starts at revision 0 (`pt_next_rev`, `upreset.c:925`), and the stale revision r (1..127) wins against 0 in either scan order (`upreset.c:486`). The stale bytes go away only when their chunk happens to be rewritten for another slot (`pt_build` keeps only directory records).
- **Fix sketch:** in `pt_scan_img`, mark a chunk that holds a well-formed record the directory does not point to (a 3-byte mask). `pt_wipe` and the restore path then rewrite marked chunks too (`pt_write(c, UP_SLOTS, 0)`); or simply rewrite each marked chunk once at the first quiet moment after boot. About 80-120 B flash, 3 B RAM, main loop, no audio change.
- **Test:** `patch` group, simulated NOR: cut power after the first write of a move, boot, RESTORE the slot, boot, and expect the factory sound; the same with a new save instead of RESTORE.
- **Known?** not recorded (the store's header says "a record that moved to another chunk exists twice for a moment: the newer wins", which is true until a restore).

### E4. Settings changed from the editor's MENU tab are written to flash on every request, with no rest time  (P3, SUSPECTED, backend)
- **What the player meets:** Dragging a MENU value in the web editor (TUNE, CLICK LEVEL...) with nothing sounding can trigger one 4 KB settings erase per request that reaches the unit: wear on the two settings sectors, and a 17-40 ms LED / screen drop each time. On the unit the same rows are written once the knob has rested ~2 s.
- **Why (code):** `editor_menu.c:92-94` (`ed_menu_save`) calls `settings_save()`, which writes at once when `autosave_quiet()` is true (`project.c:515-549`). The device path debounces with `ui.mset_dirty` / `mset_t` (`ui_menu.c:1033-1038`). How many requests a drag sends depends on the web's `queueWrite` coalescing (`web/editor/app.js:119`).
- **One check settles it:** count `felucca_dbg.erases` (TEST screen, or the emulator) during a 2 s slider drag in the editor's MENU tab.
- **Fix sketch:** in `ed_menu_save`, use the device debounce (set `ui.mset_dirty`, `ui.mset_t`) and answer rc 4 "queued"; about 12 B flash. The reply then no longer means "saved": check how `web/editor` treats rc 4 before changing it.
- **Known?** not recorded.

### E5. A `--release` build accepts the developer switches, so leaving the serial console out depends on the builder's environment  (P3, CONFIRMED, backend)
- **What the player meets:** nothing with the published b6, as long as it was built without `DUELL_TEST_MODE`, `DUELL_BENCH` or `FELUCCA_CDC` in the environment. But nothing enforces that: a release built with one of them set ships the CDC console (`uboot` and the bench / test words) and the test screens.
- **Why (code):** `tools/build.py:362-367` passes `FELUCCA_CDC`, `DUELL_TEST_MODE`, `DUELL_BENCH`, `FELUCCA_OTA_DRYRUN` and `FELUCCA_OTA_RAMONLY` straight through from the environment; `--release` refuses only `DUELL_VELO_CAPTURE` (`build.py:389-390`).
- **Fix sketch:** with `--release`, stop the build when any of `FELUCCA_CDC=1`, `DUELL_TEST_MODE=1`, `DUELL_BENCH=1`, `FELUCCA_OTA_DRYRUN=1`, `FELUCCA_OTA_RAMONLY=1` is set (3-5 lines of Python; no firmware bytes).
- **Test:** the `test_site_build.py` / release-tool tests: a `--release` call with `FELUCCA_CDC=1` must fail.
- **Known?** not recorded.

## Roadmap suggestions
1. b7: E1 (editor save keeps End B, with the real byte-for-byte test) and E2 (dialog words, INSTALL / QUICKSTART lines). Both are small and touch no audio code.
2. Add a rule to the U4 row (24 multis) and to any use of the reserved 0xEA000..0xFBFFF: every sector there must keep its last 256 bytes (0xF00..) erased, as patslot and fm6_vbank do. The update loader erases any sector in 0xE0000..0xFBFFF whose tail passes its update-record check (`ldr_core.c:171-179`, window `loader.c:20`). The autosave (0xE5000 / 0xE6000) already breaks this rule, since its 3840-byte payload covers 0xF00..0xFFF. A false match is about 2^-32 there, so it is no defect today, but a new store should not repeat it. A `_Static_assert` per new object costs nothing.
3. Before 1.0.0 stable: E3, the cleanup of stale patch records (one boot-time mask, one rewrite).
4. E5 with the next release-tool change; check E4 with one erase count before changing anything.
