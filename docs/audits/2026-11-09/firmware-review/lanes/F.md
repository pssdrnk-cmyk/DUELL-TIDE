## What is solid
- Two-core hand-off (`twocore.h` / `twocore.c` / `twocore_run.c`): one writer per word, sequence-numbered jobs, core 1 the only decider, take / yld / claim answered exactly once; the deadline and wait limit are bounded by the half; the fault paths (refused, word ahead, no answer, hang 100 ms, flash park timeout) all fall back to core 0 with a fade of a half-written part 2. The one race left (core 1 still running after a very-late block while core 0's next events / `mix_sends` touch part 2) is already recorded in `docs/TWOCORE_STAGE1.md` 8.8 as a fault-path-only case; not re-reported.
- Engine switch while sounding (`voice.c` `engine_block`): the old engine fades 4 blocks on its own `pe_old` values, its memory is re-claimed only after the fade, waiting notes start on the new engine. INSERT type switch (`fx.c` `track_insert`): fades out, state zeroed before the new type starts. No buffer of one type is read by another.
- Patch / project / undo swaps on the main loop are done under `fm1_irq_off` (`project.c:348`, `ui.c:1339`, `upreset.c:1273`), and in normal play core 1 only runs inside core 0's audio interrupt, so those sections also exclude core 1. The scope tap (`fx.c` `wv_tap`) is one writer per part with the counter published after the entries; the reader (`ui_scope.c:378`) keeps clear of the block being written.
- USB audio: asynchronous endpoint, the ring's fill held in a band by +-1 frame packets (covers the 44,117.6 / 44,100 drift), an empty ring repeats the last frame, a full one drops a block; a host that stops reading is detected after 20 ms and the feed stops, re-primed with silence on return. The DAC output does not depend on USB at all. The 48 kHz resampler's ring guard (`n + n/8 + 2`) covers its 35 frames a block.
- Start-up: core 1 halted first, WDT and boot guard before the RAM unpack, the unpack works in the pool before the pool is cleared and the hashes are checked after the `.bss` clear (`ramplace_boot`, 3 tries then UBOOT); core 1 started at the stock supplies before the audio interrupt; core 1's stack (3 KB, 1,744 B measured) has its own limit. Overrun: misses counted per DMA period, the ease ladder fed by the elapsed half including TIMER5's nested work; TIMER5 keeps USB audio served while nested.
- Delay times at tempo extremes: `beat_samples` guards BPM < 40, `delay_samples` halves until the time fits and floors at 16 samples, the callers keep the plain / PING-PONG reads inside half the line. The compressor's coefficients floor at 1 sample (`cmp_coef`); the limiter's divide is only taken above `LIM_T`.

## Findings (most important first, at most 15)

### F1. Loading a saved sound while you play cuts notes the other part is holding  (P2, CONFIRMED, functional)
- **What the player meets:** part 1 holds a chord or a HOLD drone (more notes than one core could play for this scene; the two-core NOTES numbers allow more). Select part 2 and load one of your own saved sounds (a USER / saved slot, not a factory sound), or load a multi or a pattern from the store. At once part 1 loses notes: first its release tails, then its oldest held notes fade out in one block. They do not come back while the keys stay down (a latched drone stays thinner until it is played again). Factory sounds do not do it (they are read from the program flash, not through the store driver). A MIDI program change that selects a saved slot probably goes the same way (not traced).
- **Why (code):** every store read goes through `st_read` (`storage_hw.c:7-24`), which first calls `tc_flash_park` (`twocore.c:127-139`): `tc.park = 1`, and it stays set until `tc_watch`'s next main-loop pass (`twocore.c:122`, called from `main.c:276`). The load path is `upreset.c:1259 up_load` -> `up_rec` -> `pt_raw` (`:516-531`) -> `pt_rd` (`:416-421`) -> `st_read`. In the audio interrupt `tcr_begin` (`twocore_run.c:565-575`) sees `one = ... || tc.park`; on the first such block `!bd_one_now` sets `tcr.trim = 3`, then `voice_trim_now(&trk[0])` runs at once and part 2's in `tcr_play2` (`:534-537`). `voice_trim_now` (`voice.c:328-350`) fades every voice above `trk_nvoice`, which now reads the one-core `bnotes1` (`voice.c:143`) instead of the two-core `bnotes`. The comment at `budget.c:356` shows the trim on a park is intended ("a flash park is short: the runner trims to the one-core numbers for it"), but a park is held for the rest of the main-loop pass, and the notes it fades are gone, not paused. The park is only needed while a flash window has the XIP map off, and those windows run with interrupts off (`irq_save`), so no job can be posted during one; the only job that can be open then is the fault-path very-late job.
- **Fix sketch:** don't hold `tc.park` across blocks for a read. In `st_read` / `st_prog` / `st_erase`, check `tc_closed()` inside each IRQ-off window (with interrupts off no new job can start; if a fault-path job is still open, wait up to `TC_PARK_US` as now, then `tc_fail(TCR_FLASH)`), and drop `tc.park` (or keep it only for the OTA path). Then `bd_one_now` never flips for a store read and nothing is trimmed. About -20 to +20 B flash, 0 RAM; the audio interrupt's code is unchanged (it just never sees `tc.park`). Keep the trim for real pauses and faults.
- **Test:** `tcstage1` / the twocore simulation's `park` scene: with two-core numbers above the one-core ones and a held chord over the one-core number on part 1, a store read must leave `tcs.trims` at 0 and the voice count unchanged; the `park_stuck` scene keeps its FLASH strike.
- **Known?** not recorded (KNOWN_ISSUES / KNOWN_LIMITS say only "no notice for the second core"); the design intent is in the `budget.c:356` comment.

### F2. About 10.6 KB of flash is a second copy of the effect code for bus B  (P3, SUSPECTED, backend)
- **What the player meets:** nothing today; it is the largest flash reserve found in this lane (4.8 KB are free).
- **Why (code):** `fx.c` includes `fx_bus.c` twice (bus A with the `fx`, `hl`, `rev_comb`, `dly_buf` globals; bus B with `fx_b`, `hl_b`, `rev_comb_b`, `dly_buf + DLY_HALF` and `BUS_FN(f) f##_b`), unconditionally, so every reverb model, the delay paths, SHIM and SPRING exist twice; bus B runs only in DUEL / SPLIT. The `_b` symbol sizes listed in `docs/audits/2026-11-08/flash-hot/REPORT.md` (b4-era ELF, the only size data present; no `.map` or ELF is in the review checkout) add up to 10,598 B: `dly_ev_b` 2,032, `rev_plate_b` 1,614, `rev_hall_b` 1,394, `dly_mod_b` 958, `rev_shimx_b` 902, `rev_spring_b` 616, `rev_reso_b` 596, `rev_shim_b` 444, `spring_glide_b` 422, `rev_room_b` 354, `dlyev_read_b` 286, `rev_locut_b` 286, `rev_tail_b` 212, `hall_gains_b` 114, `rev_fadeout_b` 104, `cho_zrun_b` 86, `rev_byp_b` 70, `rev_run_b` 62, `rev_switch_b` 22, `fx_buses_ev_b` / `fx_buses_mod_b` 12 each. The space audit (`docs/audits/2026-11-09/space/REPORT.md`) did not list it.
- **Fix sketch:** one copy of the bus code taking a bus pointer (a struct of the bus's state and its line pointers, and `splitb` as a field) instead of the macro-expanded globals. Net saving estimated ~9 KB (10.6 KB less some growth of the one copy for base-register addressing). It touches the audio interrupt's effect loops: the CPU effect is unknown (loops already hold global addresses in registers, so it may be neutral, may not); it needs the unit sweep with DUEL (M08) and the host bit-exactness pins. A large change: only when a feature needs the room.
- **Test:** the existing render pins (`wave`, `xvalues`, the bus tests) must stay bit-exact; the FM-1 CPU sweep with a DUEL multi before and after.
- **Known?** not recorded (the flash-hot report lists the twins for placement only).

### F3. A USB recording gets a hard gap and two clicks when the unit writes its flash  (P3, CONFIRMED, functional)
- **What the player meets:** recording the FM-1 into a computer over USB audio with the transport stopped (held notes, a drone) and saving a sound, a setting or anything else: the speaker / headphones get the soft dip (fade out, silence, fade in), but the USB recording jumps from full level to nothing for about 17-40 ms and back. Saves are refused while the transport plays, so it is a stopped-only case.
- **Why (code):** `audio.c:110-145` ducks only the DAC buffer (`duck_half` after `uac_tap`, "USB (uac_tap) is not ducked"); `st_erase` (`storage_hw.c:47-73`) then runs the erase inside `irq_save` (`cli`, `hal/fm1_flash.h:240`), so TIMER5 cannot run `uac_service` (`timer5.c`, `usb.c:1212`) and the host's 1 ms isochronous IN tokens find no packet (`uac.missed`). The frames rendered before the erase are still in the ring, so the stream resumes at full level.
- **Fix sketch:** give the USB tap the same gain as the duck: in `audio_block`, when `duck_on || duck_g < 32768`, fade the block before `uac_tap` (or apply `duck_g` inside `uac_tap`), so the recording fades to silence before the gap and back after it. About 40-60 B, audio interrupt (only around a flash write). The gap itself cannot be removed (the XIP map is off).
- **Test:** host group of the duck (`ovl` / storage duck tests): with the UAC ring fed, the frames written to `ua_ring` during the ducked halves fade to 0 and back.
- **Known?** not recorded.
